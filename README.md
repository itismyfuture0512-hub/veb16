# Менеджер задач (To-Do) — Вариант 16

Лабораторный практикум: **Контейнеризация многокомпонентных приложений с помощью Docker Compose**.

Приложение состоит из **4 контейнеров**, объединённых в одну docker-сеть:

| Компонент     | Технология                | Порт (хост) | Назначение |
|---------------|---------------------------|-------------|------------|
| `frontend`    | Nginx + Vanilla JS        | `8080`      | Веб-интерфейс с 2 кнопками |
| `backend`     | Python 3.12 + FastAPI     | `8000`      | REST API, CRUD-операции с БД, вызов web-service |
| `db`          | PostgreSQL 16             | `5432`      | Хранение задач и статусов, инициализация через `init.sql` |
| `web-service` | Python 3.12 + FastAPI     | —           | Сервис приоритезации и расчёта сроков задач |

## Реализованный вариант (№16)

**Тематика web-сервиса:** Менеджер задач (To-Do) — сервис приоритезации и расчёта сроков задач
**Данные для БД:** список задач и статусы их выполнения

### Функциональность

- **Кнопка 1 «Показать задачи из БД»** — `GET /api/tasks`: backend читает список задач из PostgreSQL.
- **Кнопка 2 «Рассчитать приоритеты и сроки»** — `POST /api/tasks/prioritize`: backend отправляет открытые задачи в `web-service`, получает балл приоритета, категорию и рекомендуемый срок, **сохраняет результаты в БД** и возвращает обновлённый список.

### Формула приоритета (web-service)

```
score = 40 * importance/5 + 45 * urgency/5 + 15 * (1 - min(hours, 40)/40)
```

- `importance`, `urgency` — 1..5
- `hours` — оценка трудоёмкости

Категории: `critical` (≥80), `high` (≥60), `medium` (≥40), `low` (<40).

Дедлайн рассчитывается последовательным планированием: задачи сортируются по убыванию балла,
каждой выделяется `ceil(hours / 8)` рабочих дней, сроки идут каскадом от текущей даты.
Дополнительно вычисляется риск срыва относительно срока, указанного пользователем.

## Запуск

```bash
# 1. Клонировать репозиторий
git clone <URL_РЕПОЗИТОРИЯ>
cd lab-docker-compose

# 2. Создать .env из примера
cp .env.example .env

# 3. Собрать и запустить все 4 контейнера
docker compose up --build -d

# 4. Открыть приложение
# http://localhost:8080
```

### Проверка статуса

```bash
docker compose ps
docker compose logs -f backend
```

### Остановка

```bash
docker compose down          # остановить, данные БД сохранятся в volume db_data
docker compose down -v       # остановить и удалить volume (сброс БД)
```

## API

### Backend (`http://localhost:8000`)

| Метод  | Путь                        | Описание |
|--------|-----------------------------|----------|
| GET    | `/api/health`               | Проверка доступности backend и БД |
| GET    | `/api/tasks`                | Список задач (кнопка 1) |
| POST   | `/api/tasks`                | Создание задачи |
| PATCH  | `/api/tasks/{id}/status`    | Изменение статуса задачи |
| DELETE | `/api/tasks/{id}`           | Удаление задачи |
| POST   | `/api/tasks/prioritize`     | Расчёт приоритетов и сроков через web-service (кнопка 2) |

### Web-service (внутри docker-сети `http://web-service:8000`)

| Метод | Путь            | Описание |
|-------|-----------------|----------|
| GET   | `/health`       | Health-check |
| POST  | `/api/priority` | Пакетный расчёт приоритетов и сроков |

## Особенности конфигурации Docker Compose

- **`depends_on` + `condition: service_healthy`** — backend стартует только после готовности PostgreSQL и web-service.
- **`healthcheck`** у `db` (`pg_isready`), `web-service`, `backend` и `frontend`.
- **`volumes`** — именованный том `db_data` сохраняет данные PostgreSQL между перезапусками.
- **`init.sql`** монтируется в `/docker-entrypoint-initdb.d/` и выполняется при первом старте БД (схема + первичные данные).
- **Переменные окружения** — вынесены в `.env` (шаблон в `.env.example`).
- **Внутренняя сеть** `todo-net` — контейнеры обращаются друг к другу по именам сервисов.
